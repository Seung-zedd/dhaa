# 파일시스템 기반 LLM 에이전트 메모리: 조직화, 진화, 지속가능성

> **원문**: Filesystem-Based Memory for LLM Agents: Organization, Evolution, and Sustainability
> arXiv:2607.26637v1 (2026-07-29) · UIUC, UCSD, UC Merced, Adobe Research, TAMU (Jiawei Han 랩)

---

## 1. 한 줄 요약

배포된 에이전트들이 당연하게 쓰고 있는 "메모리 = 마크다운 파일트리" 방식을 **처음으로 체계적으로 검증한 연구**. 결론은 조건부다 — 정리(organization)가 확실히 사주는 건 **검색 비용**이지 **정답률이 아니다**.

---

## 2. 문제 설정

### 왜 이 주제인가

- LLM 에이전트는 컨텍스트 윈도우를 넘는 기간(세션 수개월)에서 동작해야 함
- 학계는 각자 전용 메모리 표현(지식그래프, 요약뱅크, 임베딩 트리 등)을 설계해 왔지만, **실무는 그냥 파일시스템으로 수렴**했다
  - Anthropic memory tool (파일 연산 6개)
  - Claude Code의 인덱스된 memory 폴더
  - `AGENTS.md`, Skills 같은 레포지토리 마크다운
- 파일시스템의 장점: 검사 가능(inspectable), 이식 가능, 에이전트가 이미 능숙한 도구로 조작, **폴더 구조 자체가 택소노미**

### 검증되지 않은 두 가지 가정

1. 메모리가 쌓이고 충돌하고 낡아가는 동안에도 **에이전트가 스스로 정리 상태를 유지할 수 있다**
2. 그 정리가 **비용값을 한다**

기존 대응책들은 증상만 치료한다는 지적:
- 학계의 메모리 연산은 항목 단위(add/update/delete)일 뿐 **저장소의 형태를 건드리지 않음**
- 업계의 "dreaming"(OpenAI) / "Dreams"(Anthropic)는 **에이전트 바깥에서** 주기적으로 통째로 재구축 — 에이전트 자신의 쓰기가 "국소적이고 점진적"이라 그 사이에 저장소가 썩는다는 걸 전제한 설계

## 3. 형식화: 하나의 저장소, 세 개의 역할

```
Execution Agent  ──(trajectory / conversation chunk)──▶  Management Agent
       ▲                                                       │
       │                                                       ▼
       └──────────(retrieved skills / answers)──── Memory Filesystem (M₁→M₂→…→M_T)
                                                               ▲
                          Search Agent ─────(traverse, cite)───┘
```

| 역할 | 계약 | 하는 일 |
|---|---|---|
| **Management Agent** | `M_t = m(ι, x_t, M_{t-1})` | 들어오는 청크를 통합·재구성·유지보수. 생성/재작성/병합/분할/이동/삭제 전권 |
| **Search Agent** | `(a, Γ) = s(ι, q, M)` | 저장소를 탐색해 **출처 인용이 붙은 답변** 반환 (읽기 전용) |
| **Execution Agent** | `e(τ, Γ) = (ξ, z)` | 실제 태스크 수행. 궤적이 곧 다음 입력 청크가 됨 |

**핵심 주장**: 선언적 메모리(사실·선호·규칙)와 절차적 메모리(skills)를 **하나의 저장소가 함께 서빙**한다. 코딩 에이전트에서는 세 역할을 한 모델이 다 할 수도 있다.

### 저장소 구조

파일 `f = (경로, 한 줄 설명, 본문)`. YAML frontmatter(`name`, `description`)가 검색의 1차 표면. 마크다운 헤딩이 파일 아래로 택소노미를 이어감. 사실에는 인라인 출처 locator(`[S6T5]` = 6세션 5턴). 중복은 복사 대신 **cross-reference**.

### 택소노미 계약 (P1~P5)

| | 원칙 | 내용 |
|---|---|---|
| P1 | 형제 구별성 | 이름(최악의 경우 이름+설명)만으로 형제를 구분할 수 있어야. 본문을 열어야 구분된다면 라벨 실패 |
| P2 | 형제 관련성 | 한 부모 아래 있는 것들은 함께 있을 만해야 |
| P3 | 부모-자식 포괄성 | 부모 이름이 선언한 범위를 자식이 벗어나지 않고, 그 범위의 내용은 전부 그 아래 있어야 (→ 하위트리를 다 뒤졌으면 결론을 내려도 됨) |
| P4 | 트리 전역 근접성 | 관련이 깊을수록 트리상 가까이 |
| P5 | 구조적 경제성 | 구조는 검색을 위한 것. 라우팅에 도움 안 되는 계층은 오버헤드 |

## 4. 실험 설계

**벤치마크**
- 대화형: LoCoMo(158문항), PersonaMem 32k/128k(객관식, 판정자 불필요), REALTALK(21일 실제 메시징)
- 절차형: ALFWorld 140 태스크 (6개 goal family), **leak-free 프로토콜** — 태스크 i는 i 이전 태스크로만 만든 저장소를 씀

**6가지 메모리 변형**

| 변형 | 설명 | 빌드 비용 |
|---|---|---|
| Closed-book | 저장소 없음 (하한선) | 0 |
| Chunk retrieval | 원본을 청크로 쪼개 BM25 인덱싱 (표준 RAG 대조군) | 0 |
| Verbatim dump | 세션당 1파일, 내용 그대로 (무큐레이션 기준선) | 0 |
| Foldered sessions | dump의 파일들을 **이동만** 해서 폴더 택소노미 부여 (바이트 편집 0) | 최저 |
| Reorganized (preserve / condense) | LLM이 dump를 재구조화. 두 버전은 "모든 사실 보존" 규칙 한 줄 차이 | 중간 |
| Agent-curated | 빈 저장소에서 스트림 따라 management agent가 구축 | 최고 |

**변인 4개**: 저장소 형태 / 스트림 규모 / 툴 하네스 / 백본 모델 강도 (nano → mini → gpt-5.4)

**측정**: 정답률·인용 지지율 + **비용**(라운드·토큰·읽은 분량) + **저장소 건강도**(초기 메모리 생존, 갱신 정확도) — 종점이 아니라 **성장 곡선**으로

## 5. 핵심 결과 (RQ1~RQ5)

### RQ1 — 에이전트는 어떤 저장소를 만드는가

- 모두 **주제 기반 트리**를 만들지만, 그 형태는 **스케일이 아니라 모델의 지문(signature)**
- 자료가 많아지면 **샤딩이 아니라 통합(consolidate)** — 계층이 폴더/파일에서 **파일 내부 헤딩으로 이동**
  - PersonaMem 32k → 128k(스트림 5배): 폴더 3개·파일 12개 → **폴더 1개·파일 2개**, 대신 섹션 53개 → **210개**
- 같은 스트림, 모델만 바꾸면 파일 수가 **122 / 2 / 105**로 요동 (nano / mini / gpt-5.4). 자릿수 단위 차이
- **파일 개수는 조직화 정도를 말해주지 않는다**: "파일 2개" 저장소가 트리로 보면 깊이 6, 평균 팬아웃 11로 다수 파일 저장소보다 깊다
- **가장 명백한 병리**: 재구조화를 시키면 모델이 **말없이 내용을 압축·유실**시킨다. "모든 사실을 보존하라" 규칙 **한 줄**을 넣어야 멈춤

### RQ2 — 형태가 값을 하는가

**정답률: 어디서나 이기는 형태는 없다.**

| 메모리 | LoCoMo | PM 32k | PM 128k | REALTALK |
|---|---|---|---|---|
| Closed-book | 18.4 | 34.4 | 47.6 | 10.6 |
| Chunk retrieval | 81.6 | 71.9 | 66.7 | 71.8 |
| Verbatim dump | 84.2 | **78.1** | 69.0 | 77.6 |
| Foldered sessions | **86.1** | 62.5 | **76.2** | **77.6** |
| Reorg. (preserve) | 82.9 | 56.2 | 59.5 | 77.6 |
| Reorg. (condense) | 79.1 | 68.8 | 54.8 | 41.2 |
| Agent-curated | **86.1** | 37.5 | 66.7 | 75.3 |

- **가장 싼 구조화(Foldered sessions)가 가장 일관된 선두** — 이동만 했는데
- 가장 공들인 Agent-curated가 PM 32k에서 **최악(37.5)**. 인용 정확도는 거의 만점인데 **선택을 틀림** → 사실 누락이 아니라 **표현의 문제**(부록 D.1)
- 인용 지지율은 어떤 형태든 82~98%로 균일 → **파일시스템 저장소는 형태와 무관하게 검증 가능한 근거를 제공**

**확실한 이득은 검색 비용이고, 자료가 클수록 커진다.**
- PersonaMem(대용량): 정리된 저장소가 dump 대비 쿼리당 검색 단가를 **절반 이하로** (4.0¢ → 1.4¢ / 3.9¢ → 1.6¢)
- 작은 대화 벤치마크: 거의 동률 (2.1~2.5¢)
- 메커니즘: 툴 호출은 **더 많이**(4~5 → 7~9회) 하지만 한 번 읽을 때 **훨씬 적은 토큰**을 당긴다

**스킬 쪽은 승자가 소비자에 따라 뒤집힌다.**

| 메모리 | 강한 실행자(gpt-4.1) | 약한 실행자(gpt-4.1-mini) |
|---|---|---|
| No store | 73.6 | 52.9 |
| Episode log (원본 궤적 그대로) | **87.1** | 66.4 |
| Curated skills+mem (GS, 가이던스 합성) | 82.1 | **76.4** |

- 실행자 등급을 낮추면 Episode log는 **21점** 손실, GS는 **6점** 손실
- 무효 액션 비율: Episode log 19%→36%, GS 12%→22%
- → **원시 궤적은 그걸 소화할 만큼 강한 실행자를 요구하고, 태스크용으로 쓰인 가이던스는 우아하게 열화한다**
- 메모리는 **약한 실행자에게 더 값지다**(+23.5 vs +13.5), 그리고 그쪽이 배포 비용도 더 싸다

### RQ3 — 백본 모델 능력

**대화형: 쓰기 능력은 스타일만, 읽기 능력이 점수를 산다.**

| Management Agent | 정답률 | 검색 단가 | 파일/폴더/섹션 |
|---|---|---|---|
| gpt-5.4-nano | 73.8 | 3.2¢ | 122 / 12 / 413 |
| gpt-5.4-mini | 66.7 | 2.6¢ | 2 / 1 / 210 |
| gpt-5.4 | 71.4 | 3.8¢ | 105 / 4 / 561 |

- 구조는 자릿수로 다른데 **정답률은 7점 밴드 안에서 단조성조차 없음**
- 반면 **Search Agent를 바꾸면 단조 상승**: 62 → 71 → 79
- 가장 강한 search agent도 **가장 공들인 저장소를 가장 못 읽음**(nano 빌드 83.3 vs gpt-5.4 빌드 71.4)
- **단, 경계가 있다**: 빌드 자체가 실패하고 있던 PM 32k에서는 curator를 gpt-5.4로 올리자 12/32 → 18/32로 회복. **쓰기가 병목인 곳에서만 쓰기 능력이 값을 한다**

**절차형: 능력이 임계값(threshold)으로 작동한다.**

| Curator | All | heat | cool | 저장소 |
|---|---|---|---|---|
| nano | 75.0 | 6.2 | 68.0 | 114 파일 |
| mini | 76.4 | 43.8 | 48.0 | 45 파일 |
| gpt-5.4 | **89.3** | 75.0 | 84.0 | **16 파일** |

- 하위 두 모델은 **통계적 동률**(114 vs 45 파일 차이에도), 최상위만 +13점 점프
- 스키마 준수와 게이팅 규율은 **모든 모델이 지킴** → 능력이 사주는 건 **형식 준수가 아니라 증류(distillation) 품질**
  - nano는 heating 관련 항목을 12개나 성실히 파일링하고 heat 점수 6%
  - gpt-5.4는 조밀한 heat 항목 2개로 75%
- **가장 강렬한 결과**: gpt-5.4가 큐레이션한 저장소를 **약한 실행자(mini)**가 쓴 결과(89.3)가, **강한 실행자(gpt-4.1)**의 모든 셀(Episode log 88.6 포함)을 능가 → **누가 실행하느냐보다 무엇이 큐레이션됐느냐가 더 중요**

### RQ4 — 성장 속에서의 지속가능성

**좋은 소식**
- 140 태스크 / 한 대화 지평 안에서 **모든 변형이 뒤로 갈수록 좋아지고, 아무것도 퇴화하지 않았다**
- **초기 메모리는 압도적으로 생존** (삭제·재작성은 얇은 조각). "방치로 썩는" 현상은 관측 안 됨
- 축적된 경험이 **실행자 능력을 대체**: mini의 Episode log가 초반 35태스크 51.4% → 마지막 35태스크 91.4%
- 큐레이션은 성숙기에 들어감: gpt-5.4 저장소는 최종 16파일 중 14개가 태스크 35까지 생성 완료, 이후엔 편집·병합만
- **강한 큐레이션 = 교체가 아니라 넓은 제자리 편집(in-place maintenance)**

**나쁜 소식**
- **큐레이션 비용은 절대 상각되지 않는다**: 저장소가 다 자란 뒤에도 에피소드당 6~12 라운드를 계속 씀
- **택소노미 계약 준수는 저장소가 자라면서 침식**된다. 이걸 거의 유지한 건 가장 강한 management agent 하나뿐
- Episode log의 "다 서빙" 방식은 **저장소 크기에 비례해 검색 비용이 상승** ($7.88 vs GS $2.97 / 140태스크)
- 큐레이션이 곧 압축은 아니다: LoCoMo 저장소는 원본 스트림보다 **35% 더 커짐**(구조·해소된 참조·locator 추가). PersonaMem 128k는 1/4로 압축

### RQ5 — 하네스(툴셋)

- **툴을 하나 추가**(BM25) → 행동은 바뀌지만(에이전트가 실제로 사용) **결과는 안 바뀜** (통계적 동률)
- **툴셋을 교체**(bash shell) → **저장소 자체가 재편**됨. 그 폭이 모델 교체와 맞먹음
  - PersonaMem 128k: 파일 툴 1~2개 파일 vs **Shell 147개 파일** (모델 동일, 툴만 다름)
  - 스킬 세팅: Shell이 mini curator의 **최고 성적**(82.9%) — heat 81%로 gpt-5.4 curator보다도 높음
- 방향은 세팅이 결정: **긴 대화에서는 샤딩+동률, 스킬에서는 통합+승리**
- Search agent가 **주어진 저장소에 스스로 적응**: 다파일 저장소에선 BM25를 54회 호출, 단일 거대 파일에선 2회만 쓰고 목차를 걸어 읽음
- → **하네스는 중립적 래퍼가 아니라 메모리 조직화의 레버**

## 6. 결론

> 파일시스템 기본값의 두 가정에 대한 답은 갈린다.
> 에이전트는 **측정한 모든 지평 안에서 저장소를 유용하고 건강하게 유지할 수 있다.** 다만 얼마나 잘 정리되어 있느냐는 management agent 능력에 종속된다.
> **정리가 값을 하느냐는 조건부다** — 자료에, 메모리를 소비하는 에이전트에, 손에 쥔 도구에.
> 그리고 **우리가 측정한 어떤 에이전트도 정리 자체를 더 나은 답으로 전환하지 못했다.**

실제로 결과를 움직인 레버 세 가지:
1. **쓰는 에이전트의 능력** (다만 쓰기가 병목일 때만)
2. **메모리가 서빙되는 형태** (원본 vs 증류된 가이던스 — 소비자에 맞춰)
3. **큐레이션에 쓰이는 도구** (하네스)

## 7. 실무 관점 정리 (에이전트 하네스 설계자용)

| 상황 | 권고 |
|---|---|
| 자료가 작다 | 정리에 돈 쓰지 마라. verbatim dump + 좋은 search agent로 충분 |
| 자료가 크다 | 정리는 **검색 비용**으로 회수된다. 정답률 향상은 기대하지 마라 |
| 저비용 구조화가 필요 | **Foldered sessions** — 파일 이동만으로 택소노미 부여. 가성비 최고 |
| 재구조화 패스를 돌린다 | **"모든 사실을 보존하라" 규칙을 반드시 명시**. 안 하면 조용히 유실됨 |
| 소비자가 강한 모델 | 원본 궤적/로그를 그대로 줘라 |
| 소비자가 약한 모델 | 태스크별로 **합성된 가이던스**를 줘라 (열화 내성) |
| 예산 배분 | 대화형이면 **search 쪽에**, 절차형(증류 필요)이면 **curation 쪽에** |
| 도구 설계 | 툴 추가는 행동만 바꾼다. **툴셋 교체가 구조를 바꾼다**. 원하는 구조를 유도하는 노브로 쓸 수 있음 |
| 장기 운영 | 큐레이션 비용은 상각되지 않는다. 택소노미 침식을 **모니터링**해야 함 |

## 8. 한계 (저자들이 명시한 것)

- 저장소 빌드는 **단일 draw**. reasoning 모델의 run-to-run 편차가 실제로 큼 (툴 설명 한 줄 수정만으로 2파일 → 29파일)
- 문항 수가 작음(32~158). LoCoMo 재판정 시 ±1.3점 이동 → **몇 문항 차이는 시사적일 뿐**
- PersonaMem 32k/128k는 길이만 다른 게 아니라 **대화 자체가 다름** → 순수 스케일 테스트 아님
- 지평이 짧다: **한 대화 / 140 태스크**. "수개월 누적"은 측정 못 함
- LoCoMo gold 158문항 중 **4개가 실제로 결함**(부록 D.2에 카탈로그화). 제거해도 순위는 불변
- 남은 열린 문제: 벤치마크가 저장소 형태에 거의 **눈이 멀어 있다**는 점, 그리고 한 대화를 넘는 지평
